## 1. やるべきこと (DO)

開発の進行に合わせて、以下の順序（ステップ1〜6）でワークフローを進めてください。

### 【ステップ1：準備】
### 1.1 トピックブランチの作成
* **ブランチの作成**: 新機能の実装やバグ修正を行う際は、必ず `main` ブランチの最新状態からトピックブランチを新規作成して切り替えてください。
  * ブランチ名プレフィックス例: `feat/add-xxx`, `fix/bug-yyy`, `chore/setup-zzz`

### 【ステップ2：開発・テスト】
### 1.2 テストコードの作成・更新の義務化
* **テストの作成**: 新しい機能、データ変換ロジック、計算・ソート処理などのコアロジックを実装・変更した際は、必ず対応する自動テストコードを `src/__tests__/` 配下に新規作成、または既存のテストファイルを更新してください。

### 1.2.5 データベーススキーマ変更のマイグレーション管理
* **直接更新の禁止**: Supabase のダッシュボード上で直接テーブルやインデックスを新規作成・更新する操作（手動のSQLエディタでの適用など）は、手元のローカルマイグレーションファイルと乖離するため原則禁止します。
* **マイグレーションファイルの作成**: スキーマの変更（テーブル定義、インデックス、ポリシーなど）を行う際は、必ず Supabase CLI を用い、以下のコマンドでマイグレーションSQLファイルを生成して管理してください。
  ```bash
  npx supabase migration new <マイグレーション名>
  ```
* **変更の適用**: ローカルや本番データベースへの適用は、ファイル書き込み後に `npx supabase db push` コマンドを使用してCLI経由で適用してください。

### 【ステップ3：検証】
### 1.3 コミット・プッシュ前のローカル検証
* **事前チェック**: コードをリモートへプッシュする前に、必ずローカルで以下のコマンドを実行し、エラーが発生しないことを確認してください。
  ```bash
  npm run test   # 自動テストの実行
  npm run lint   # 静的解析の実行
  npm run build  # プロダクションビルドの確認 (TypeScript型チェック含む)
  ```

### 【ステップ4：履歴整理】
### 1.4 プルリクエスト (PR) 作成前のコミット集約 (1PR 1コミットの徹底)
* **履歴のSquash（一本化）**: プルリクエストを作成してリモートへプッシュする前に、必ずトピックブランチ上のコミットログを1つの綺麗なコミットに集約してください。
* **集約手順 (git reset --soft の使用)**:
  ```bash
  # 1. main からの変更をすべてステージング状態に戻す
  git reset --soft origin/main
  # 2. すべての変更を1つのまとまったコミットメッセージでコミット
  git add -A
  git commit -m "feat: xxx の実装"
  ```

### 【ステップ5：PR作成・CI監視】
### 1.5 プルリクエスト (PR) の作成と CI ジョブの監視
* **PRの作成**: コミットが1つにまとまった状態でリモートへプッシュし、GitHub上で `main` に対するPRを作成します。
  * **PRテンプレートの使用**: プルリクエスト作成時には、必ずリポジトリ内の `.github/PULL_REQUEST_TEMPLATE.md` に定義されたテンプレートを読み込み、チケットリンク、変更概要、特別な作業内容、および備考を漏れなく記述してください。
  * コマンド例: `gh pr create` (GitHub CLIを使用する場合、自動的にテンプレートの枠組みが読み込まれます)
* **CIの監視**: PR作成後は、GitHub Actions 上の「マージ前自動チェック」が正常にパス（グリーン）するまで、進捗状況（コマンド: `gh pr checks` 等）を監視してください。
* **エラーの即時デバッグ**: もしCIが失敗した場合は、ただちに実行ログ（コマンド: `gh run view` 等）を確認し、原因となったエラーをデバッグして修正コミットを追加でプッシュしてください。

### 【ステップ6：マージ】
### 1.6 プルリクエスト (PR) のマージ
* **反映手順**: 全てのCIチェックが成功したことを確認してマージします。
  * コマンド例: `gh pr merge --merge --delete-branch`

### 【ステップ7：リリース】
### 1.7 バージョンの更新とGitHubリリースの作成
* **package.jsonのバージョン更新**: リモート（GitHub）へリリースを公開する際は、必ず事前に `package.json`（および `package-lock.json`）の `"version"` を更新してください。
  * 更新の基準はセマンティック・バージョニングに従います（新機能・ツール導入は `MINOR`、バグ修正のみは `PATCH` をインクリメント）。
* **変更の反映**: バージョンの変更についても、直接 `main` にコミットせず、バージョン更新用のトピックブランチ（例: `chore/bump-version`）経由でプルリクエストを作成し、`main` にマージしてください。
* **GitHubリリースの作成**: `main` にバージョン更新がマージされた後、最新のコミットに対してタグ（例: `v1.1.0`）を付与し、GitHubの「Releases」にて、タイトル（`v1.1.0`）およびリリースノートを添えてリリースを作成してください。

## 2. やってはいけないこと (DON'T / NEVER)

### 2.1 セキュリティに関する禁止事項
* **機密情報（APIキー等）のコミット禁止**: `.env` や `.env.local` などの、実際のデータベース接続URL、外部サービス用のAPIキー、認証トークンなどの機密情報が含まれる環境変数ファイルを Git の管理対象に追加（コミット）しないでください。これらは常に `.gitignore` で除外された状態を維持してください。

### 2.2 Git操作に関する禁止事項
* **main ブランチへの直接変更 of 禁止**: 決して `main` ブランチがチェックアウトされた状態でファイル変更のコミットを作ったり、直接 `main` へプッシュ（`git push origin main`）を試みたりしないでください。
  * **エラー発生時のリカバリー**: ローカルの Husky やリモートの Branch Protection により、`main` でのコミットやプッシュはエラーとして自動的にブロックされます。もし誤って `main` ブランチのまま作業を進めてしまいコミットがブロックされた場合は、以下のコマンドで変更を保持したままトピックブランチへ切り替えてからコミットをやり直してください。
    ```bash
    # 1. 変更を保持したまま新しいブランチへ切り替える
    git checkout -b <トピックブランチ名>
    # 2. そのブランチで通常通りコミットを行う
    git add -A
    git commit -m "feat: xxx"
    ```


### 2.3 開発プロセスに関する禁止事項・ガイドライン
* **コミット集約前のプッシュ・PR作成の禁止**: ローカルでの開発中に作成した雑多な作業コミット（`wip` や `fix error` など）を、1つにまとめないままリモートへプッシュしたり、プルリクエストを作成したりしないでください。
* **ローカル検証を通していないコードのマージ禁止**: `npm run test` や `npm run build` をローカルで通していないコードをプルリクエストとしてマージしないでください。本番環境へのデプロイがクラッシュする原因になります。
* **ドキュメント（README等）の連動更新の義務化**: 機能の実装やロジック・仕様の変更（UIの差し替え、新規オプションの追加、DBスキーマの変更など）を完了した際は、必ずコミット前に `README.md` などのプロジェクトドキュメントに影響がないかを確認し、記述を最新化してください。ドキュメントの更新は、コードの修正と乖離させず、原則同じトピックブランチ（およびプルリクエスト）内に含めて同時にマージしてください。
